# 全自动媒体流水线验证与回滚观察方案

## 目标

用一条主线命令先验证单栏目，再扩展到三栏目全量运行，同时保证出现异常时能快速定位到具体 `source_id`、具体阶段和具体输出物。

## 运行前检查

确认以下配置已经就绪：

- `VOLCENGINE_APP_KEY`
- `VOLCENGINE_ACCESS_TOKEN`
- `VOLCENGINE_RESOURCE_ID`
- `OSS_ACCESS_KEY_ID`
- `OSS_ACCESS_KEY_SECRET`
- `OSS_BUCKET`
- `OSS_ENDPOINT`
- `CONTENT_LLM_API_KEY`
- `CONTENT_LLM_BASE_URL`
- `CONTENT_LLM_MODEL`
- `.pipeline/series_map.json`
- `.pipeline/youtube_sources.json`

## 第一阶段：单栏目冒烟验证

先只跑一个栏目，建议从 `tiandi` 开始：

```bash
python3 scripts/run_full_pipeline.py --series tiandi --wait
```

这一步需要确认：

- `scripts/download_youtube.py` 只同步 `tiandi`
- `scripts/transcribe_batch.py` 只处理 `tiandi`
- `scripts/normalize_transcript.py` 只整理 `tiandi`
- `scripts/split_to_wechat_articles.py` 只拆 `tiandi`

重点观察以下文件：

- `.pipeline/logs/latest_status.json`
- `.pipeline/logs/events.jsonl`
- `.pipeline/logs/runs/*.summary.json`
- `.pipeline/manifest.json`
- `天地大道/`
- `拆解后文章/`

单栏目通过标准：

- 下载阶段没有把其他栏目混进来
- manifest 中新增或修复的条目都使用稳定 `source_id = series_key/title_key`
- 新转录条目带有 `sequence`、`title_key`、`display_title`、`audio_sha1`
- 自动拆稿后的文章文件名使用稳定期号，如 `03-01_xxx.md`
- 若已有文章文件冲突，manifest 中对应条目会被标记为 `article_status = failed`，而不是静默覆盖

## 第二阶段：单栏目幂等复跑

同一条命令连续再跑一次：

```bash
python3 scripts/run_full_pipeline.py --series tiandi --wait
```

复跑需要重点确认：

- 没有新视频时，下载阶段只记日志，不产生重复音频
- 已完成且磁盘完整的拆稿条目不会重复生成
- manifest 与磁盘一致时，只会做状态修复或跳过，不会重复覆盖

## 第三阶段：全量运行

单栏目稳定后再跑全量：

```bash
python3 scripts/run_full_pipeline.py --wait
```

全量运行时重点看：

- 三个栏目是否都只落在各自目录
- `.pipeline/logs/events.jsonl` 中是否能按 `module` 和 `series_key` 区分问题
- `latest_status.json` 和各个 `runs/*.summary.json` 是否能对上本轮行为

## 分阶段隔离排查

如果需要缩小问题范围，可以使用这些命令：

只跳过下载：

```bash
python3 scripts/run_full_pipeline.py --series tiandi --skip-download --wait
```

只跳过拆稿：

```bash
python3 scripts/run_full_pipeline.py --series tiandi --skip-split --wait
```

只重做规范化：

```bash
python3 scripts/normalize_transcript.py --workspace-root . --series tiandi --force
```

只重做拆稿：

```bash
python3 scripts/split_to_wechat_articles.py --workspace-root . --series tiandi
```

## 回滚与修复原则

这条流水线的回滚不依赖“整仓库回退”，而是按 `source_id` 做局部修复。

### 下载阶段

- 如果是错误下载或错误重命名，先从 `.pipeline/logs/events.jsonl` 定位 `series_key` 和 `display_title`
- 删除错误音频后，重新执行 `scripts/download_youtube.py --series <series_key>`

### 转录阶段

- 如果 manifest 状态异常，但原始长稿和转录文件还在，优先修正 manifest 对应条目
- 如果源音频已被删除，但需要重跑，可重新执行对应栏目的下载，再执行：

```bash
python3 scripts/transcribe_batch.py --workspace-root . --series <series_key> --wait
```

### 拆稿阶段

- 如果自动拆稿结果不满意，但文件已经生成，先删除 manifest 记录中的 `article_paths`
- 再把对应条目的 `article_status` 改回 `pending`
- 然后重新执行：

```bash
python3 scripts/split_to_wechat_articles.py --workspace-root . --series <series_key>
```

- 如果只是出现“部分文章文件已存在”，不要强制覆盖，先人工清理残留文件，再重新拆稿

## 建议的观察顺序

每次运行后建议按下面顺序看：

1. 先看 `.pipeline/logs/latest_status.json`
2. 再看 `.pipeline/logs/events.jsonl` 中最近一批事件
3. 再对照 `.pipeline/manifest.json` 的具体 `source_id`
4. 最后看栏目目录和 `拆解后文章/` 的实际文件

这样可以最快判断问题是在下载、转录、规范化还是拆稿阶段。
